# 初版方案审查与优化记录

本文是对 ai-app-template 初版设计文档（六周路线图版）的审查结论。
保留原方案的判断（市场空白、能力组合、目标人群全部成立），
以下是修正过的问题。修改后方案已全部实现于本仓库。

## 审查结论总表

| # | 初版方案 | 问题 | 优化后 |
| --- | --- | --- | --- |
| 1 | Week1 CLI 叫 `agent-forge`，Week6 发布 `pip install ai-app-template` | 一个项目两个名字，品牌分裂 | 全链路统一 `ai-app-template`（仓库/包/模块/命令，ADR-1） |
| 2 | docker-compose 一键启动 Redis + PG + LangFuse | MVP 代码对 Redis/PG 零引用，纯 cargo cult | 砍掉；观测栈降级为可选 profile（ADR-2） |
| 3 | 模板 = LangChain 全家桶生态 | 依赖重、版本耦合、调试黑盒，不利教学 | 只用 LangGraph + openai SDK + pydantic（ADR-3） |
| 4 | 「交互式 CLI」 | 脚本/CI 无法交互 | 保留交互，同时提供 `--template/--yes` 非交互路径 |
| 5 | 测试排在各周「配套」位置 | 测试后置 = 边写边腐化 | 测试先行贯穿；生成的项目必须**离线全绿**（ADR-5） |
| 6 | LangFuse「接入配置」 | 未定义接入方式，容易写成侵入式埋点 | 客户端类替换式接入，零侵入（ADR-4） |
| 7 | PyPI 发布排在第 6 周 | 反馈回路太长 | v0.1 本地可 `pip install -e .` 即时验证；PyPI 尽早发 alpha |
| 8 | 三模板并列，未定义组合方式 | 全量复制会有三份漂移的骨架 | base + 变体叠加 + `_overlay.json` 废弃清单（ADR-7） |
| 9 | 成本路由未定义实现 | 容易过度设计成「模型」 | 规则启发式起步，接口留学习型升级位（ADR-8） |
| 10 | 「面试弹药」只在 README 层面 | 弹药需要能讲出来才算 | 配套九篇教程 + 面试话术指南（docs/tutorials/） |

## 关键取舍的展开说明

### 为什么坚持「离线全绿」是底线

初版路线图里评测、测试都真实调用 API。这会让：新用户体验门槛 = 有 Key + 有预算；
CI 跑一次测试花一次钱；演示翻车率随网络波动。改成 Fake 替身体系后，
生成的项目 `pytest -q` 与 `run_eval --mock` 零成本全绿，真实调用只在
用户显式配置后发生。**「能离线验证的绝不在线验证」**从此成为模板的工程信条。

### 为什么评测要区分 mock 与 live 门槛

初版没有区分。实践暴露：替身数据是静态/词法的，拿真实质量的门槛
（关键词命中率）去卡 mock 跑分，要么永远红、要么逼着把门槛调到形同虚设。
正确做法是两层：mock 验管道（CI 每次跑），live 验质量（配 Key 手动/定时跑）。

### 为什么 README 说「LLM 增强而非 LLM 依赖」

初版节点的隐含假设是 LLM 调用成功。真实供应商的限流、超时、区域故障
会让工作流随机 500。优化后每个节点都有明确兜底：重试（extract）、
全量保留（review）、确定性拼接（summary）、诚实拒答（rag 的知识库未命中）、
预算收尾（multi-agent）。整套行为都有对应测试证明（`test_llm_*_degrades_*`）。

### 路线图重排（相对初版）

初版六周线性排列（CLI→网关→图→结构化→观测→打磨）。优化为**纵切**：
每周都交付一个「能生成、能测试、能跑通」的完整切片，避免任何一周
结束时存在「写了但不能验证」的代码：

| 周 | 交付切片 |
| --- | --- |
| 1 | CLI + base 模板最小版（parse+summary 两节点）+ 离线测试 |
| 2 | 网关三件套（重试/降级/熔断）+ ScriptedClient 测试 |
| 3 | 结构化输出 + 解包 + extract/review 节点 + 条件边 |
| 4 | 评测体系（mock/live 双门槛）+ rag-agent 变体 |
| 5 | multi-agent 变体 + LangFuse + Docker |
| 6 | 文档教程 + CI + PyPI alpha + 发布文章 |

（本仓库已一次性交付了全部六周的产物，此表同时作为课程设计的参考大纲。）
