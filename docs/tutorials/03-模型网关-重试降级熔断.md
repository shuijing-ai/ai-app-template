# 03 · 模型网关：重试、降级、熔断

> 目标：精读 `templates/base/app/llm/gateway.py`（约 300 行），
> 掌握 LLM 调用层的三大弹性机制，并能回答所有相关面试追问。
> 这是整个仓库含金量最高的一篇。

## 0. 为什么需要网关

没有网关时，每个节点各自 `client.chat.completions.create()`：

- 重试逻辑复制 N 份，参数各异
- 供应商故障时没有统一降级点
- token 与成本无人统计
- 想加全链路埋点要改 N 处

网关的契约只有一句话：**所有 LLM 调用必须经过 `ModelGateway.complete()`**。
职责单一、入口唯一，后面的每个能力都是在这个入口上叠加的。

## 1. 三层弹性机制的精确分工

| 机制 | 应对什么 | 时间尺度 | 位置 |
| --- | --- | --- | --- |
| 重试 retry | 瞬时抖动（限流/超时/网络） | 秒级 | `_try_model` 内层循环 |
| 降级 fallback | 单模型持续不可用 | 分钟级 | `execute` 遍历链 |
| 熔断 breaker | 避免对已知坏掉的模型反复砸请求 | 分钟~小时级 | 每模型一个 CircuitBreaker |

记忆法：**重试治抖、降级治坏、熔断治浪费**。

### 1.1 什么样的错误才值得重试

```python
def is_retryable(exc):
    if isinstance(exc, (RateLimitError, APITimeoutError, APIConnectionError)):
        return True
    return isinstance(exc, APIStatusError) and exc.status_code in RETRYABLE_STATUS
```

429/408/5xx 可重试；401（鉴权错）与 400（参数错）重试一万次也不会成功——
**不可重试错误直接落到降级**。这个区分是面试最常见的第一个追问。

### 1.2 指数退避 + 抖动

```python
delay = min(cap, base * 2 ** (attempt - 1))
delay += random.uniform(0, jitter)
```

- 指数：第 1/2/3 次失败后等 1s/2s/4s，给供应商恢复窗口；
- 上限 `cap`：别等出超时；
- 抖动 `jitter`：多个客户端同步重试会造成「雷群效应」，
  随机化让重试在时间上摊开。

### 1.3 降级链：跨供应商才是真降级

```python
"standard": ["flash", "backup"],   # flash=gpt-4o-mini, backup=deepseek-chat
```

同一供应商的两个模型可能一起挂（区域故障）。链上放**不同供应商**
的模型，单点故障才真正被消除。`LLMResponse.fell_back` 记录本次是否
用了非首选模型——这是监控「主模型健康度」的核心指标。

### 1.4 熔断器状态机（30 行版本）

```
closed --连续失败达阈值--> open --冷却期到--> half-open --一次成功--> closed
                              |                      |
                              +----探测又失败---------+--> open
```

`open` 状态下 `allow()` 返回 False，请求**根本不发出去**（省时省钱）；
`half-open` 只放行一次探测。工业级实现（如 sentinel）还有滑动窗口计数，
这里刻意用最简版本：**先让概念跑起来，复杂度按需加**。

## 2. 代码走读：一次 complete() 的完整路径

```
complete(request)
  ├─ router.classify(文本, task, structured) → RouteDecision(tier, reasons)
  ├─ router.chain_for(tier) → FallbackChain(["flash","backup"])
  └─ execute(chain, request)
       for alias in chain:                    # 降层级
         if not breaker.allow(): continue      # 熔断跳过
         resp = _try_model(alias, request)     # 重试层（内层循环）
         if resp: resp.fell_back = alias != 首选; return resp
       raise GatewayExhaustedError(...)        # 全挂：交给节点兜底
```

两个设计点：

1. **路由只做决策，网关只做执行**。`classify` 返回的 `RouteDecision`
   带着人话 reasons（"输入超长 → 升 heavy"），直接进日志——
   可解释性不是事后补的，是返回值结构的一部分。
2. **client_factory 是唯一的 IO 注入点**。生产注入 `OpenAI`（或 LangFuse
   埋线版），测试注入 `ScriptedClient`。观测与测试共用同一个缝，
   这是本仓库最值得抄的模式（ADR-4）。

## 3. 成本核算：让每一分钱可见

```python
cost = prompt/1e6 * price_in + completion/1e6 * price_out
```

模型注册表带价格，`GatewayStats` 按模型聚合调用量/失败率/token/成本，
`/health` 接口直接吐 `summary()`。当老板问「这个月模型花了多少钱、
哪个环节花的」，答案是一个 HTTP 请求而不是查账单。

注意精度坑：单次调用成本在 1e-6 美元量级，`round(x, 6)` 会把
4.5e-6 四舍五入成 5e-6（真实踩过的坑，测试 `test_cost_estimation_and_stats`
守护着这个精度）。

## 4. 测试走读：替身怎么写才精确

`ScriptedClient`（`app/llm/fakes.py`）按**模型 ID** 脚本化行为：

```python
handlers = {
  "gpt-4o-mini":  lambda kw: raise_429(),      # 一直限流
  "deepseek-chat": lambda kw: "from-backup",    # 备份正常
}
```

于是四个关键场景各成一个 5 行断言的测试（tests/test_gateway.py）：

| 测试 | 证明 |
| --- | --- |
| test_retry_with_backoff_then_success | 失败两次第三次成功，attempts==3 |
| test_non_retryable_error_falls_back_immediately | 401 类错误零重试直接切换 |
| test_circuit_breaker_opens_and_skips_model | 熔开后 flash 只被真实调用 1 次 |
| test_all_models_exhausted_raises | 全挂抛 GatewayExhaustedError |

构造 openai 异常需要 httpx.Request/Response 包装——这种「测试基建」
本身就是 LLM 工程师的日常功夫。

## 6. 自测题（面试模拟）

1. 重试、降级、熔断分别解决什么问题？没有熔断只有重试+降级会怎样？

3. `fell_back=True` 的比例突然升高，你会先查什么？
4. 为什么链上建议放不同供应商的模型？这引入了什么新问题？（提示：密钥管理、
   数据合规、成本模型不同）
