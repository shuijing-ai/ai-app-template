# 06 · 可观测性与自动化评测

> 目标：让系统「看得见」（LangFuse/结构化日志/统计），
> 让质量「管得住」（评测集 + 双门槛 + CI 门禁）。
> 代码：`app/observability/`、`app/utils/logger.py`、`app/eval/`。

## Part 1 · 可观测性

### 1.1 零侵入接入：替换客户端类

`langfuse_setup.py` 的全部魔法：

```python
def get_openai_client_factory():
    if observability_enabled():
        from langfuse.openai import OpenAI as LangfuseOpenAI   # 同接口、自动埋线
        return LangfuseOpenAI
    return _default_openai
```

网关初始化时 `client_factory = get_openai_client_factory()`——
之后每次 `chat.completions.create` 的输入输出、token、延迟都被自动上报。
**业务代码零改动；没装 langfuse / 没开开关时零影响。**

这个设计复用了测试注入点（教程 03）：一个缝，两个用途。
自托管 LangFuse 的一键栈在 `docker-compose.yml` 的 `observability` profile 里。

### 1.2 结构化日志：JSON 一行一事件

`utils/logger.py` 用标准库 logging + 自定义 Formatter 输出 JSON：

```python
logger.info("extract 完成", extra={"ctx": {"node": "extract", "attempt": 1}})
# → {"ts":"...","level":"INFO","logger":"...","msg":"extract 完成","ctx":{...}}
```

为什么不用 print / 不上 structlog：JSON 行可以直接被任何日志平台检索；
自己写 Formatter 让「结构化」两个字完全透明（教学价值）。

### 1.3 业务指标的免费出口：/health

网关的 `GatewayStats`（按模型聚合调用量/失败/token/成本）与全部
熔断器状态在 `/health` 直接暴露。运维不需要接 LangFuse 也能看到
「谁在失败、谁在花销、谁被熔断」——**最低成本的黄金指标面板**。

## Part 2 · 自动化评测

### 2.1 评测集：质量变成可回归的数字

`app/eval/test_cases.py` 只描述输入与期望信号：

```python
EvalCase(id="contract-risk", document=CONTRACT_DOC,
         expect_keywords=["违约", "交付"],   # 应出现在 findings+summary
         expect_min_findings=2)
```

铁律：**评测集只绑定「期望」，不绑定实现**。换模型、改提示词、调路由，
评测集一个字不改——跑分才能横向对比。

### 2.2 双门槛：mock 验管道，live 验质量

```python
if mock:
    passed = schema_valid            # 流程走完 + 输出可解析
else:
    passed = hit_rate >= threshold and schema_valid and count >= min_findings
```

为什么必须分（ADR-9 的实战由来）：替身是静态/词法的，拿质量门槛卡
mock 跑分，要么永远红、要么把门槛调成摆设。分开后：
**mock 进 CI**（每次提交免费跑），**live 手动/定时跑**（配 Key 后）。

### 2.3 指标选型的克制

只用四个指标：关键词命中率、schema 合法率、产出数量、延迟。
没有 BLEU/ROUGE（与「好不好」弱相关）、没有 LLM-as-judge（引入第二个
不稳定系统）。**指标少而硬，评测才会被坚持跑下去。**

### 2.4 CI 门禁：退出码即纪律

```
python -m app.eval.run_eval --mock && pytest -q
```

低于阈值 → 退出码 1 → CI 红。产出物 `eval_results/report.md`
是 Markdown 表格，直接贴进 PR——评审者第一眼看到的是数字不是形容词。

### 2.5 离线替身的两层设计

| 替身 | 层级 | 适用 |
| --- | --- | --- |
| `FakeGateway`（节点级） | 网关接口 | 跑通图/评测管道；review-flow 版是**输入感知**的（词法风险表命中即报） |
| `ScriptedClient`（SDK 级） | openai 客户端 | 精测网关自身的重试/熔断/降级 |

节点级替身测**编排**，SDK 级替身测**弹性机制**——层级错了，
要么测不到故障路径，要么替身比实现还复杂。

## 2.6 动手练习

1. 给 run_eval 增加 `--json` 输出模式（机器可读），供 CI artifact 归档。
2. 写一个 nightly 脚本：live 模式跑评测，结果追加到 `eval_history.jsonl`，
   画出关键词命中率随提示词版本的变化。
3. 进阶：实现 LLM-as-judge 的 `--judge` 模式，同时思考：judge 自身的不稳定
   怎么控制？（采样多次取多数、固定温度、judge 也进评测集）

## 2.7 自测题

1. 为什么观测接入选择「替换客户端类」而不是装饰 gateway.complete？
2. /health 暴露网关统计有什么安全考量？（提示：内部指标外泄）
3. mock 门槛如果也卡关键词命中率，会发生什么连锁反应？
4. 你的产品经理要求「准确率提升 3%」——用本篇的四指标体系怎么回应？
