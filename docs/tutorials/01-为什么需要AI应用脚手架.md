# 01 · 为什么需要 AI 应用脚手架

> 目标：说清楚这个项目解决的真问题、市场空白在哪、边界在哪。
> 这一篇本身也是「项目立项文档」的写作示范。

## 痛点：从 demo 到生产之间隔着十几件脏活

任何人都能在 notebook 里五十行代码调通一个 LLM。但把它变成**服务**时，
会立刻撞上一串没人替你做好的事：

| 阶段 | 脏活 | 不做的后果 |
| --- | --- | --- |
| 调用 | 重试、超时、限流处理 | 供应商抖动 = 服务抖动 |
| 成本 | 什么任务用贵的模型 | 月底账单惊魂 |
| 稳定性 | 主模型挂了的降级 | 单点故障全站 500 |
| 输出 | 模型返回的「野 JSON」 | 下游解析随机崩 |
| 质量 | 改一版提示词无法回归 | 「感觉变好了」 |
| 排障 | 出问题不知道哪环错 | 全靠肉眼猜 |

这些脏活与业务无关、跨项目高度重复 —— 正是脚手架该吸收的部分。

## 市场空白的三层论证

写立项文档时，「没人做」必须拆成可验证的三个子命题：

1. **形态空白**：搜索 "langgraph template" 得到的绝大多数是静态仓库
   （`git clone` 或 Download ZIP），不是可安装的 CLI（`pip install` 后
   一条命令交互式生成）。前者无法做「项目名替换、变体选择、后续升级」。
2. **能力组合空白**：同时具备 成本路由 + 降级兜底 + 结构化输出体系 +
   自动化评测 的开源模板几乎不存在——多数模板只覆盖其中一两项。
3. **受众空白**：以上能力普遍以「大厂内部平台」的形态存在，
   中小团队与个人开发者只能看文章脑补。

> 练习：去找 3 个 star 数最高的 LangGraph/Agent 模板仓库，逐项核对
> 它们覆盖了上面表格里的哪些行。把结论写成半页纸——这就是你的
> 「竞品分析」面试素材。

## 边界：这个项目不做什么

立项文档里「不做什么」比「做什么」更能体现判断力：

- **不做运行时框架**：生成的项目零 ai-app-template 依赖，生成完即可删掉
  脚手架——模板是「毕业设计」不是「终身会员」。
- **不做模型评测平台**：评测模块只做「能进 CI 的轻量回归」，
  不复刻 OpenAI Evals / ragas 的全部功能。
- **不锁供应商**：一切 OpenAI 兼容接口（DeepSeek/Qwen/vLLM/OneAPI）
  改配置即用，不引入任何单家 SDK 的私有特性。
- **不做低代码**：生成的代码是给工程师读的，全部显式、可调试。

## 一条命令的价值模型

```
传统路径：clone 模板 → 手动改项目名 → 补缺失件 → 踩配置坑 → 半天起步
脚手架：  ai-app-template create my-app -t rag-agent --yes → 5 分钟到全绿测试
```

价值不在「省了多少分钟」，而在**起点即规范**：新人拿到的第一个 commit
就带着测试、评测、网关与降级——工程习惯从第一天就被代码本身教育。

## 自测题

1. 「静态模板仓库」与「CLI 脚手架」的本质差异是什么？（提示：可演进性）
2. 如果面试官问「为什么不直接用 LangChain 的全部能力？」——用 ADR-3 的
   三个理由回答。
3. 你的目标用户里，「求职者」和「中小团队」对脚手架的诉求差在哪？
   （提示：教学文档 vs 起步速度）
