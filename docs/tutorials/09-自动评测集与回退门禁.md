# 09 · 自动评测集与回退门禁（auto-eval）

> 前置：[06 可观测性与自动化评测](06-可观测性与自动化评测.md)（评测四指标与
> mock/live 双门槛）。本篇讲它的进阶形态：**只给一张身份卡，自动生成
> 边界/异常/对抗用例；每次改提示词，按影响面重跑；与基线对比后直接
> 告诉你该不该回退**。设计全文见 [docs/designs/auto-eval-design.md](../designs/auto-eval-design.md)。

## 1. 为什么手写评测集不够

教程 06 的种子用例是手写的，三个问题随之而来：

1. **冷启动贵**：换了业务域（审阅→简历筛选），重写一套用例要半天；
2. **覆盖偏**：人手写用例天然偏向 happy path，边界和对抗场景总是缺；
3. **变更后不敢动**：改提示词没有「变好还是变坏」的机器判断，
   质量回归靠感觉。

auto-eval 用「生成一次固化永久 + 基线签字制 + 回退判定」三件套解决。

## 2. 身份卡：唯一要写的东西

`app/eval/identity.json`（各模板自带示例，改成你的业务即可）：

```json
{
  "identity": {
    "name": "合同风险审阅助手",
    "description": "输入中文商务文档，输出结构化风险发现与汇总结论",
    "quality_policy": { "recall_bias": true, "refuse_out_of_scope": true }
  },
  "generation": { "per_taxonomy": 3, "tiers": ["happy", "boundary", "anomaly", "adversarial"] }
}
```

`recall_bias` 会影响生成器的用例倾向（宁多报 → 产出更多「漏报惩罚」型用例）。
`input_examples` 可选但强烈建议：越真实的样例，生成越贴业务。

## 3. 生成流水线：LLM 生成 + 确定性校验

```bash
python -m app.eval.gen_cases              # 生成全部层级并固化
python -m app.eval.gen_cases --tier boundary --dry-run   # 只看校验结果不落盘
```

流水线（`gen_cases.py`）四步，每步都值得面试展开：

1. **组装生成请求**：身份卡 + 分类定义 → 走 `ModelGateway`（heavy 档）——
   评测生成器是网关架构的第一个内部客户，重试/降级/成本统计全享受；
2. **LLM 按 schema 输出** `GeneratedCaseSet`（XxxSet 约定的再次应用）；
3. **确定性后校验**（核心）：期望关键词必须**逐字出现在输入里**（防幻觉指标）、
   `empty_risk` 用例必须期望 0 发现、`min_length` 输入必须真的短、
   批内 + 与种子集去重。不过即剔除，剔除原因逐条打印；
4. **固化**到 `app/eval/generated/{tier}.json`（进 git，可手改，手改优先）。

**为什么「生成一次固化永久」**：跑分时现生成用例 = 每次换考卷，
回归对比失去意义。生成是手动操作，绝不进 CI。

## 4. 分类矩阵：边界与异常的 11 种标准姿势

`taxonomy.py` 固定了分类学（LLM 只按类填充）：贴下限输入、无风险文档、
无标题格式、emoji 字符集、高密度风险（boundary）；域外问题、损坏输入
（anomaly）；提示注入、诱导编造（adversarial）。想调整覆盖面改这张表，
一条注释都不用动别处。

注意职责边界：**模型宕机/非法输出等服务异常归单元测试**
（`test_llm_total_outage_*`），评测集只承载业务质量——两类验证的失败
语义和修复方式完全不同。

## 5. 套件化重跑与基线签字

```bash
python -m app.eval.run_eval --suite all         # 种子 + 全部生成集
python -m app.eval.run_eval --suite boundary   # 只跑边界
python -m app.eval.run_eval --suggest          # 不知道跑什么？问它
python -m app.eval.run_eval --set-baseline     # 满意后签字固化
```

`--suggest` 读 git 变更文件按影响映射打印建议（改了节点提示词 → 全量；
只改文档 → 无需重跑）。它是提示制而非全自动——消除决策成本，
不消灭人工确认。

基线（`app/eval/baseline.json`）是**签字认可制**：只有显式
`--set-baseline` 才更新。生成新用例或 `gen_cases --force` 后旧基线
即失效，需重新签字——基线不允许悄悄滑坡。

## 6. 回退判定：四档结论

每次 live 跑分自动与基线对比，输出：

| 结论 | 触发条件 | 退出码 |
| --- | --- | --- |
| `rollback` 建议回退 | 总分跌超 5pp，或非焦点套件跌超 10pp | 1（CI 直接挡） |
| `warn` 人工确认 | boundary/adversarial 焦点套件跌超 15pp | 0 |
| `improve` 可固化 | 总分升超 5pp | 0 |
| `pass` 通过 | 其余（容差内） | 0 |

两个设计细节：

- **焦点套件为什么阈值更宽**：边界/对抗输入天然最不稳定，轻微退化先警告
  人工确认而不是直接判死刑。实施时还修正了原设计的一个矛盾——若焦点
  套件同时适用 10pp 回退线，15pp 警告线永远不可达（>15 必然先 >10）；
- **抗波动**：临界场景用 `--runs 3`，同一套件连跑三次，逐用例
  **多数决**、命中率取**中位数**后再判定。mock 模式禁止 `--runs`
  （替身是确定性的，多次采样无意义——和 mock 不做回退判定同理）。

## 7. 一次完整的质量回归（动手）

```bash
# 在任一模板生成项目里（需 API Key）：
python -m app.eval.gen_cases                    # 1. 生成并固化用例
python -m app.eval.run_eval --suite all         # 2. 全量跑分
python -m app.eval.run_eval --set-baseline      # 3. 签字固化基线
# 4. 故意把 extract 提示词改差（比如删掉「不要编造」）
python -m app.eval.run_eval --suggest           # 5. 它会告诉你：改了节点 → 全量重跑
python -m app.eval.run_eval --runs 3            # 6. 三次采样判定 → 观察 rollback
git checkout -- app/graph/nodes/                # 7. 回退，重跑回到 pass
```

第 6→7 步就是这套体系的全部价值：**回退不再是直觉，是退出码**。

## 8. 自测题

1. 为什么生成用例必须固化，不能每次跑分现生成？
2. 确定性后校验为什么把「关键词不在输入里」视为幻觉指标？
3. `--set-baseline` 为什么要求显式执行，而不用「历史最好成绩」自动更新？
4. 焦点套件（boundary/adversarial）的判定阈值为什么比普通套件宽？
5. `--runs 3` 的多数决中位数，各抑制了哪种噪声？
6. 服务异常（模型宕机）为什么不放进评测集？

## 9. 延伸

- 读 `app/eval/compare.py`：60 行实现完整回退判定状态机；
- 读 `app/eval/gen_cases.py` 的 `validate_case`：每条拒绝理由对应一类
  LLM 生成物缺陷；
- 想加新类别（如「长上下文记忆」）：在 `taxonomy.py` 加一行
  `SubKind`，生成器自动覆盖——数据驱动配置的又一次胜利。
